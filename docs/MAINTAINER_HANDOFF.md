# 接手说明

## 当前基线

`data/release.json` 登记公开 0.5.14 的条数、字体方案与游戏 EXE 签名。`data/export-provenance.json` 记录来源摘要。导出的译文来自当前工坊构建对应的回交稿；维护者工作区中另有改动的草稿未混入。

`base.jsonl` 为原版参考；`mod.jsonl` 为英文前置 1402798020 的对应文本；`gff.jsonl` 为局部字段组。GFF 的 5,603 组对应 7,022 处，映射在 `data/gff-locations.jsonl`。保存稳定 ID 和源文本 SHA-256，避免相同编号在不同版本中对应不同原文。

## 字体和编码

原生字体系统按单字节索引，目前用四级灰度点拼成 16×16 汉字。一个字有 16 个透明列步进，点绘制和负向回退成对出现，最后重置并留出断行点。英文标签与运行时变量保持 ASCII。

0.5.14 在第 2、4……16 列将步进 128 替换为 193，编码字节长度和点序列不变。普通字体的 128/193 宽度相同，旧/新文字的普通字形位置保持一致。字幕字体 `chs_sub24` 使用 1.249/1.751 的交替步进，使绘制宽度和原生整数断行宽度均为 24px；行距为 36px。

原生断行逐字节累加 `trunc(width + 0.25)`，绘制使用浮点宽度。直接乘 1.5 会导致布局与绘制不一致。公共紧凑字体与多行说明字体的行高也不能混用，否则菜单文字可能隐藏或说明末尾截断。

在 1440p 的 4/3 缩放下，即便 1080p 已成对抵消的正负指令，也会再次出现笔画相关误差。0.1.2 的 `native/font_scale_fix.h` 用签名核对的三个字体计量调用点修正组合字体：保留浮点累计值，再对累计位置取整；只替换本汉化特征匹配的字体，其他字体回退原转换。缓存按线程、字体、行起点和缩放管理，顺序处理为线性扫描。完整字节序列与图集无需改变。

图集见 `fonts/atlases`，每个字体的 TXI 和 TPC 生成信息见配方。字形映射以 `data/current-map.json` 为准，旧研究方案不能覆盖当前版本。不要部署曾失败的 HI32 编码。

## 存档和崩溃

存档会缓存名字、物品说明等局部文本。转换工具只清除有效 StrRef、白名单显示字段和精确匹配已知文本摘要的缓存；保护主角名字、未知自定义内容及其他语言，生成副本，不覆盖原存档。

中文组合编码会显著增加消息字节数。原生兼容组件针对已核对 Steam EXE 扩容消息缓冲区；不能用字体修改、截断正文或清空存档代替。高帧修复与中文缓存兼容的入口仍需手动安装 DLL。

## 发布前

1. 从英文原版或前置核对每条 source SHA、语音和变量。
2. 验证全部 TLK 与 GFF 字段，保留脚本、资源 ID、性别与未改字段。
3. 测试菜单、读档名称、物品、日志、技能、专长、控制台回复和字幕。
4. 用保留原件的存档副本检查区域切换；测试高帧与光标时记录显示模式。
5. 发布后下载并核对内容，确认公开状态、前置与展示说明。不要声称全部剧情已通过。
